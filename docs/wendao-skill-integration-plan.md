# 问道接入旅游 BG 各业务线（Skill 模式）技术方案

## 一、背景与目标

- **总部 AI 产品**：问道（负责收口 BG 的 AI Agent 能力）
- **业务场景**：在旅游 BG 各 BU（签证 / 租车 / 用车 / 包车 / 邮轮）首页露出"问道"入口，用户用自然语言搜商品、做导购。
- **约束**：算法资源紧张，不做 Agent-to-Agent（以下简称 A2A）。
- **替代方案**：各 BU 把"商品查询等 API + 使用说明"封装成 **Skill**，注册给问道。问道读 Skill 描述 + 用户 Query，自行完成意图识别、参数抽取 / 追问 / API 调用 / 结果组织。

一句话概括：
> **把 BU 的能力"函数化"，让问道当成工具来调用**（类似 OpenAI function calling / MCP tool 的工程落地）。

---

## 二、技术链路（以签证为例）

### 2.1 整体时序

```
[用户] →(1)→ [BU前端: 签证首页]
                │
                │(2) 唤起问道
                ▼
           [问道前端 SDK/iFrame]
                │
                │(3) query + 上下文(bu=visa, pageCtx)
                ▼
           [问道后端 / LLM 编排]
                │
                │(4) 加载 visa 相关 Skill
                │(5) LLM 推理: 意图判定 + 入参抽取
                │(6) 参数缺失? ──是──► 追问用户 ─┐
                │                               │
                │       ◄───────────────────────┘
                │(7) 按 Skill 定义调用 BU API
                ▼
           [BU 后端 / 商品查询服务]
                │
                │(8) 返回原始数据(含 ID / URL / 枚举码)
                ▼
           [问道 后处理 / 渲染层]
                │
                │(9) 翻译/拼装 → 文本 or 卡片
                ▼
           [问道前端] →(10)→ [用户]
```

### 2.2 端到端示例

**场景**：用户打开签证首页，点击问道图标。

#### 示例 A：参数齐全，一次命中

- 用户输入：`"帮我找一个日本三年多次签证，全家四口人办，下周要用，预算每人不超过 1500"`
- 问道 LLM 根据 Skill 描述做槽位抽取：
  ```json
  {
    "destination": "JP",
    "visa_type": "三年多次",
    "people_count": 4,
    "urgency": "一周内",
    "price_max": 1500
  }
  ```
- 调用 `POST /visa/product/search`，拿到 10 个 SKU。
- 问道回答（文本+卡片）：
  > 为你找到 3 款符合"日本三年多次 / 一周出签 / 单人≤¥1500"的签证产品：
  > - **日本三年多次·标准办理** ¥1380/人，5 工作日出签 · [查看详情]
  > - **日本三年多次·加急通道** ¥1499/人，3 工作日出签 · [查看详情]
  > - ...

#### 示例 B：参数缺失，主动追问

- 用户输入：`"我想办个签证"`
- 问道 LLM 判定意图 = 商品查询，但缺 `destination`。
- Skill 中已写明 `destination` 为 required，且定义了追问话术。
- 问道回复：
  > 好的，你想办哪个国家/地区的签证呢？比如日本、美国、泰国、申根（欧洲）？

#### 示例 C：模糊参数、需要归一化

- 用户输入：`"下个月去欧洲玩一圈"`
- LLM 推理：
  - `intent = 签证商品搜索`
  - `destination = 申根` （需要 Skill 的 few-shot 示例教它"欧洲≈申根"）
  - `depart_date = 下个月`（需要 Skill 里说明日期格式 → 问道转成 `2026-06-xx`）

#### 示例 D：非商品查询的拦截

- 用户输入：`"泰国签证需要什么材料？"`
- 这条不是商品搜索，是咨询类。Skill 中可以：
  - 声明 `out_of_scope` 行为：直接让问道兜底回答；
  - 或再挂一个 `visa_policy_qa` Skill（另一接口）。

## 三、Skill 的结构

Skill 的本质是**一份"给大模型读的 API 说明书"**，重点不是让它像 OpenAPI 那样严谨，而是让它**"看懂、会用、不乱用"**。

建议字段（可以用 YAML / JSON，下面用 YAML 更易读）：

```yaml
skill_id: visa.product.search
version: 1.0.0
owner: 旅游BG-签证BU
bu: visa

# 1. 让模型判断"是否该用我"
description: |
  用于搜索 Trip.com 签证商品。当用户想要"办/买/查"某个国家或地区的签证、
  比较不同签证产品（价格/出签时长/材料简易度）、询问"我去XX需要什么签证产品"时，调用本 Skill。
  不适用于：签证政策/材料咨询、订单查询、已购签证进度。

trigger_examples:      # few-shot：提升召回与参数抽取准确率
  - query: "帮我找个日本三年多次签证"
    params: {destination: "JP", visa_type: "三年多次"}
  - query: "下周去美国，有没有加急签证"
    params: {destination: "US", urgency: "URGENT"}
  - query: "一家三口泰国签证多少钱"
    params: {destination: "TH", people_count: 3}
  - query: "欧洲签证最快几天能出"
    params: {destination: "SCHENGEN", sort_by: "process_time_asc"}

# 2. API 本体
endpoint:
  method: POST
  url: https://api.bu-visa.trip.com/open/v1/product/search
  auth: internal_jwt     # 问道网关侧配置

# 3. 参数规格——给模型看的版本
parameters:
  - name: destination
    type: string
    required: true
    description: |
      目的地国家/地区代码，ISO 3166-1 alpha-2；
      申根整体搜索使用 "SCHENGEN"；
      常见同义词："日本/岛国"=JP，"美签/美国"=US，"欧洲/申根"=SCHENGEN。
    enum_ref: /visa/meta/destinations   # 可选：运行时注入枚举
    follow_up_prompt: "你想办哪个国家/地区的签证？"

  - name: visa_type
    type: string
    required: false
    description: 签证类型。可选值：单次、二次、一年多次、三年多次、五年多次、十年多次。
    default: null

  - name: urgency
    type: enum
    required: false
    values: [NORMAL, URGENT, SUPER_URGENT]
    description: 出签加急档位。用户说"加急/急用/X天内"映射到 URGENT/SUPER_URGENT。

  - name: people_count
    type: int
    required: false
    default: 1

  - name: price_max
    type: int
    required: false
    description: 单人预算上限（人民币）

# 4. 响应处理——告诉模型怎么读返回值
response_schema:
  root: data.items[]
  fields:
    - path: product_id
      as: id
    - path: title
      as: 标题
    - path: price_rmb
      as: 价格
    - path: process_days
      as: 出签时长
    - path: cover_img
      as: 图片
    - path: jump_url
      as: 详情链接
  summarize_prompt: |
    从返回结果中挑 3 条最匹配的，按"价格-出签时长"综合排序，
    用中文给出简要推荐理由（不超过 15 字/条），最后附详情链接。

# 5. 兜底与护栏
guardrails:
  max_results_render: 5
  when_empty: "没找到匹配的签证产品，可以放宽条件试试，比如去掉预算限制？"
  when_api_error: "签证服务暂时查不了，稍后再试或到签证频道看看~"
  out_of_scope: fallback_to_llm   # 非搜索意图直接让问道兜底
```

### 对于"Skill 到底能力边界是什么"的判断

| 能力 | 是否能"只在 Skill 里写清楚就搞定" | 说明 |
|---|---|---|
| 意图是否命中本 Skill | ✅ 可以 | 靠 `description` + `trigger_examples` |
| 抽取关键入参 | ✅ 可以 | 靠参数 `description` + few-shot |
| 同义词/口语化归一（欧洲→申根、一家三口→3） | ✅ 可以 | 参数 `description` 里写规则或 few-shot 举例 |
| 枚举值（国家码等）实时更新 | ⚠️ 半自动 | 固定枚举写死；动态枚举建议提供一个 `/meta` 接口，问道启动时拉取 |
| 缺参追问 | ✅ 可以 | 每个参数写 `follow_up_prompt` |
| 多轮上下文继承（上句说了日本，下句问"办加急"） | ❓ 取决于问道 | 这个是**问道侧的对话状态管理能力**，Skill 只能声明"支持上下文"，具体由问道框架负责 |
| 多接口编排（搜索→详情→评价） | ❌ 难 | 超出单 Skill，要么拆多 Skill 让问道自行串，要么 BU 提供聚合接口 |

> 简言之：**"懂用户想什么 + 拼出参数"基本零问道工作量；"多轮对话管理 + 工具编排"是问道框架的基建，不能靠单个 Skill 解决。**

## 四、分工矩阵

| 角色 | 主要产出 | 关键事项 |
|---|---|---|
| **问道侧（平台）** | ① Skill 注册/管理后台<br>② LLM 编排（意图路由、参数抽取、追问、调用、摘要）<br>③ 工具调用网关（鉴权、限流、降级）<br>④ 卡片协议 / 渲染 SDK<br>⑤ 会话状态 & 上下文管理<br>⑥ 可观测（调用日志、bad case 回流） | 平台能力一次建设，各 BU 复用。没有这些基础设施，Skill 写得再好也跑不动。 |
| **BU 前端（以签证为例）** | ① 在签证首页嵌入问道入口（图标/悬浮球）<br>② 唤起问道 SDK，传入页面上下文（`bu=visa`, 当前浏览目的地等）<br>③ 如走卡片方案：接入卡片渲染协议（或复用问道 SDK 内置）<br>④ 点击详情链接时的 deep link 回跳 | 轻量级。核心是"入口 + 上下文透传 + deep link"。 |
| **BU 后端（签证业务线）** | ① 提供/改造对外 API（搜索、详情、可选的聚合接口）<br>② 返回**对 LLM 友好**的数据（ID 已翻译成中文、图片 URL 可直出、冗余但自解释）<br>③ 鉴权/配额/埋点 | **这是工作量最大的一块**。现有 C 端接口往往返回裸 ID、枚举码，需要做"AI 友好化"改造。 |
| **Skill 撰写侧**（可以是 BU PM + 算法/AI 工程共建） | ① 写 Skill YAML（描述、参数、few-shot、护栏）<br>② 持续收集 bad case，迭代 few-shot<br>③ 和问道一起做评测集（precision / recall / 参数抽取准确率） | 看起来像写文档，其实是**Prompt Engineering**。质量直接决定效果。 |

### 你关心的问道工作量判断

- **"教模型抽参数/追问"是否只需要写 Skill？** — **是**。前提是问道平台已经具备"读 Skill → 抽参 → 追问 → 调用"这套通用能力（这是平台级别的一次性投入，不是每个 BU 都要做一遍）。
- **问道需要为签证单独开发吗？** — 基本不需要，除非：
  - 签证有特殊鉴权/加密
  - 签证需要专属卡片样式（卡片组件可能要 UI 定制）
  - 签证有跨 Skill 编排诉求（例："先查政策再推产品"）

## 五、数据呈现的三档方案（按工作量从低到高）

> 现实中 BU API 返回的是 `product_id / country_code / cover_img_url / price_cent ...`，**模型无法直接"说人话"**。要让用户看到好的结果，需要在"数据加工"和"前端呈现"上投入。

### 方案 A：纯链接（Link-only）—— 最小可用

**做法**：Skill 调用 BU 现有"列表页跳转参数生成"接口（或者直接拼 URL），问道只回答：
> "我帮你找了 23 款日本三年多次签证，点这里看看 👉 [跳转链接]"

**工作量**：
- BU 后端：几乎 0（复用现有 URL 拼装）
- Skill：1 天可写完
- 前端：0
- 问道：0

**优点**：最快上线，最适合 POC。
**缺点**：体验差，用户被踢出对话，转化低，和"AI 导购"差异不大于搜索框。

**适用**：灰度试水、评测期、低优先级 BU。

---

### 方案 B：纯文本摘要（Text summary）—— 中等

**做法**：Skill 调用搜索 API，问道把 top N 结果**翻译成自然语言**在对话里展示：
> 为你推荐 3 款签证：
> 1. **日本三年多次·标准** ¥1380 / 5 工作日 — 材料最简单
> 2. **日本三年多次·加急** ¥1499 / 3 工作日 — 赶时间优选
> 3. **日本单次·特惠** ¥399 / 7 工作日 — 只去一次更划算
> 想看哪款详情？或者要不要筛"预算 1000 以内"？

**工作量**：
- BU 后端：**中**。需要新增/改造一个"AI 友好"接口，字段已翻译：
  - `country_code=JP` → `country_name=日本`
  - `visa_type_code=M3` → `visa_type_name=三年多次`
  - `price_cent=138000` → `price_rmb_text="¥1380/人"`
  - 建议补字段：`highlight_tags=["材料简单","当地领馆直送"]`
- Skill：2–3 天（重点是 `summarize_prompt` 和 few-shot 调优）
- 前端：几乎 0
- 问道：0（通用能力即可）

**优点**：对话沉浸感好，无额外前端开发，其它 BU 可快速复制。
**缺点**：没有图片/结构化交互，复杂信息（比较表、材料清单）表达力有限。

**适用**：**推荐作为一期主推方案**。

---

### 方案 C：结构化卡片（Rich card）—— 最重

**做法**：问道返回一段 `card_payload`（JSON），前端按预定义卡片协议渲染成商品卡，支持图片、标签、按钮（"加入对比"/"立即办理"）。

签证卡片示例字段：
```json
{
  "card_type": "visa_product",
  "items": [
    {
      "id": "V1001",
      "title": "日本三年多次签证·标准",
      "cover": "https://img.trip.com/.../jp3y.jpg",
      "price": "¥1380",
      "price_suffix": "/人",
      "tags": ["5工作日出签", "材料简单", "热销"],
      "jump_url": "https://trip.com/visa/detail?id=V1001",
      "actions": [
        {"type": "detail", "label": "查看详情"},
        {"type": "compare", "label": "加入对比"}
      ]
    }
  ]
}
```

**工作量**：
- BU 后端：**中—高**。需要聚合接口：
  - 主搜索 API
  - 可能 + 详情补全 API（评论数、销量）
  - 可能 + 图片 CDN 规格统一
  - 返回打包好的 card-ready 数据
- Skill：3–5 天（要教模型"什么时候出卡片 vs 出文本"）
- 前端：**高**。接入卡片协议，新增签证卡片组件，处理点击事件、埋点、deep link。
- 问道：**中**。需要支持"卡片返回通道 + 卡片类型注册"。这块**是否已具备是一个前置问题**，需要和问道团队确认。

**优点**：体验最接近原生搜索结果，转化率最好。
**缺点**：各 BU 卡片样式不统一会是治理难题；前端改造不小；版本升级协调成本高。

**适用**：核心 BU、流量大的场景（签证、机酒邻域导购）。

---

### 方案 D（可选·补充）：对比/决策辅助卡 —— 进阶

签证业务特别适合"**决策辅助**"：

- 用户说："日本三年多次，¥1380 和 ¥1499 差别在哪？"
- Skill 可再挂一个 `visa.product.compare` 接口，返回对比矩阵，前端渲染为"对比表卡片"：

| 维度 | 标准办理 | 加急通道 |
|---|---|---|
| 价格 | ¥1380 | ¥1499 |
| 出签时长 | 5 工作日 | 3 工作日 |
| 材料 | 在职证明+资产证明 | 在职证明+资产证明 |
| 办理渠道 | 领馆直送 | 领馆直送+加急排期 |

这是"多 Skill 串联"的典型场景，需要问道框架支持 **Skill Chaining**。

## 六、现有 API 现状对方案选择的影响（关键约束因素）

> 在实际落地中，**BU 现有 API 的成熟度和数据结构**直接决定了 Skill 接入的工作量和能支撑问道到哪一步。以下按签证 BU 可能存在的典型 API 现状分类讨论。

### 6.1 典型 API 现状分类

| 现状分类 | 典型特征 | 对接问道的影响 |
|---|---|---|
| **A. 仅有内部 RPC 接口** | gRPC / Thrift，面向内部微服务调用；无 HTTP 网关暴露 | 需要新建 HTTP 层（或在问道网关做协议转换），工作量 **+2~3 周** |
| **B. 有 C 端 BFF 接口** | REST/HTTP，但为前端页面定制；返回大量渲染字段（HTML 片段、多语言 key、嵌套对象）；鉴权走 session/cookie | 可以复用逻辑，但需：① 去除 HTML/前端专属字段 ② 补充自然语言化字段 ③ 改为 token 鉴权。工作量 **+1~2 周** |
| **C. 有开放平台/B 端接口** | 面向供应商或分销商的 API；字段规范、有文档；鉴权走 API Key | 最好改造的底子。主要补：① LLM 友好字段映射 ② 入参适配问道场景。工作量 **+3~5 天** |
| **D. 已有搜索/推荐中台接口** | 统一的商品搜索服务，支持多条件筛选、排序、分页 | 理想情况。问道直接调用，Skill 做参数映射即可。工作量 **≤3 天** |

### 6.2 签证场景常见的 API 问题与解法

以下列举签证 BU 可能遇到的**具体 API 痛点**，以及对应的解决方案和工作量评估：

#### 问题 1：返回值是 ID / 枚举码，不是自然语言

**现状举例**：
```json
{
  "product_id": "V20230815001",
  "dest_country_id": 108,
  "visa_type_id": 3,
  "process_speed_code": "NORMAL",
  "supplier_id": 5621
}
```
用户无法理解 `dest_country_id=108`，模型也很难推理。

**解法选项**：

| 解法 | 做法 | 工作量 | 推荐度 |
|---|---|---|---|
| ① BU 后端增加翻译字段 | 在返回体中增加 `dest_country_name:"日本"`，`visa_type_name:"三年多次"` | 后端 2~3 天 | ⭐⭐⭐ 推荐 |
| ② 问道侧维护映射表 | 问道缓存 BU 提供的 `/meta/countries` 等接口数据，调用后翻译 | 问道 1~2 天；BU 提供 meta 接口 1 天 | ⭐⭐ 可选 |
| ③ Skill 中写死映射 | 在 Skill YAML 里写死 `108=日本` | Skill 撰写 0.5 天；但**不可维护、不推荐** | ⭐ 应急 |

#### 问题 2：图片 URL 需要拼接 / 不同尺寸规格

**现状举例**：
```json
{
  "cover_img_path": "/visa/jp/cover_001",
  "img_host": "static.trip.com",
  "img_size_options": ["200x200", "400x400", "800x800"]
}
```
问道需要一个**完整可用的图片 URL**。

**解法**：
- **最佳**：BU 后端直接返回 `cover_img_url: "https://static.trip.com/visa/jp/cover_001_400x400.jpg"`（约定统一尺寸）
- **次选**：Skill 里写明拼接规则，让问道拼装（增加出错概率，不推荐）
- 工作量：后端 **0.5~1 天**

#### 问题 3：单次查询无法满足完整展示（需要多接口组合）

**现状举例**：签证搜索结果只返回基础信息，但用户需要看到的完整商品卡需要：
1. `搜索接口` → 基础列表（标题、价格、出签时间）
2. `详情接口` → 材料清单、退款政策
3. `评价接口` → 好评率、评论数
4. `库存接口` → 当前是否可约、最早可办日期

**影响分析与方案**：

| 方案 | 调用链路 | 问道侧工作 | BU 侧工作 | 适用 |
|---|---|---|---|---|
| **单 Skill 单接口** | 只调搜索 → 返回基础信息 | 0 | 0 | 方案 A/B（仅文本摘要） |
| **单 Skill + BU 聚合接口** | 调 1 个聚合 API → BU 内部串联多个服务 | 0 | **高**（BU 新建聚合层 1~2 周） | 方案 C（卡片）推荐 |
| **多 Skill 串联** | 问道依次调搜索 → 详情 → 评价 | **高**（问道需要支持 Skill Chaining / 工具编排） | 低（复用现有接口） | 问道平台能力就绪后 |

**签证场景推荐**：一期用"单 Skill + 基础搜索接口"（方案 B），二期由 BU 提供聚合接口升级到方案 C。

#### 问题 4：搜索条件与用户自然语言 gap 大

**现状举例**：
- 接口入参是 `departure_city_id`（int），用户说"我在上海"
- 接口入参是 `apply_date`（YYYYMMDD），用户说"下周要用"
- 接口不支持按"材料简易度"筛选，但用户说"懒得准备材料，要最简单的"

**解法**：

| Gap 类型 | 解法 | 负责方 |
|---|---|---|
| 城市名 → 城市 ID | Skill 参数里列 `enum_ref`，问道启动时加载城市映射；或 BU 提供"城市名搜索 → ID"的 meta 接口 | BU 提供 meta；问道加载 |
| 自然语言日期 → 具体日期 | 问道侧通用能力（"下周" → 当前日期 +7）；Skill 中声明日期格式 | 问道通用能力 |
| 接口无此筛选维度 | ① BU 扩展接口支持新条件<br>② 或在 Skill `summarize_prompt` 里让模型从结果中二次筛选 | 看优先级决定 |

#### 问题 5：接口限流 / 性能不满足实时对话

**现状举例**：
- 现有搜索接口 P99 = 3s（面向前端页面可以，但对话场景用户等不了）
- QPS 限制 = 50（问道高峰可能超）

**影响**：
- 慢接口 → 问道需要展示"正在查询…"占位 + 超时兜底
- QPS 不够 → 需要 BU 评估扩容 or 问道侧加缓存层

**解法**：
- Skill 声明 `timeout_ms: 5000` 和 `cache_ttl: 300s`
- 问道侧：超时返回"正在查询，稍后推送结果"
- BU 侧：评估是否需要给问道单独的流量通道

### 6.3 API 现状 × 方案 × 最终能力 映射表

下面这张表帮助你**根据现有 API 现状快速判断能做到哪一步**：

| BU 现有 API 状态 | 无改造可直接做到 | 轻量改造（≤1周）可做到 | 中等改造（2~4周）可做到 |
|---|---|---|---|
| 仅内部 RPC | ❌ 无法接入 | 方案 A（链接跳转） | 方案 B（文本摘要） |
| C 端 BFF 接口 | 方案 A（链接跳转） | 方案 B（文本摘要） | 方案 C（卡片） |
| B 端开放接口 | 方案 A/B（链接 or 文本） | 方案 B（优化文本） | 方案 C（卡片） |
| 搜索/推荐中台 | 方案 B（文本摘要） | 方案 C（卡片） | 方案 D（对比决策） |

### 6.4 API "AI 友好化"改造 Checklist（给 BU 后端的交付标准）

BU 后端可以按此清单自查，满足越多条项 → Skill 接入越顺畅、问道功能越丰富：

- [ ] **返回值含中文名称**（不仅仅是 ID/Code），如 `country_name`、`visa_type_name`
- [ ] **图片 URL 完整可访问**，无需拼接，统一尺寸（建议 400x400）
- [ ] **价格字段为人民币元**（不是分），含单位标注
- [ ] **时间字段有自然语言表达**，如 `process_days_text: "5个工作日"`
- [ ] **提供搜索结果跳转 URL**（deep link），可直接在 App/H5 打开商品详情
- [ ] **支持 JSON 格式响应**，Content-Type: application/json
- [ ] **接口鉴权支持 JWT/API Key**（非 session/cookie）
- [ ] **P95 响应时间 ≤ 2s**
- [ ] **QPS 支撑 ≥ 100**（或有独立问道流量通道）
- [ ] **有枚举/字典 meta 接口**（国家列表、签证类型列表等）
- [ ] **错误码规范**，含中文错误描述
- [ ] **分页支持**，单次最多返回 20 条

## 八、需要和问道团队对齐的关键问题清单

建议开会前就这些项目拿到明确答复：

1. **Skill 规范**：问道有没有统一的 Skill 协议（字段、版本管理、注册流程）？是否兼容 MCP / OpenAPI 转换？
2. **参数抽取能力**：是否默认支持 few-shot、同义词归一、日期/地点解析？准确率基线？
3. **多轮对话**：上下文 slot 保持几轮？是否支持槽位追问模板？
4. **调用网关**：鉴权、超时、重试、降级由谁负责？SLA？
5. **卡片协议**：是否有标准卡片协议（方案 C 的前置）？BU 自定义卡片的接入成本？
6. **评测与灰度**：有没有 bad case 回流、线上评估、灰度发布平台？
7. **成本结算**：LLM 调用费用如何在 BG/BU 间结算？是否按 Skill 维度计量？
8. **API 现状摸底**：问道是否有 API 接入标准文档？是否提供"API 友好度"自检工具或测试沙箱？
9. **多 Skill 编排**：如果一个用户 query 需要调多个接口（搜索+详情），问道是否已支持串行 / 并行 Skill 调用？
10. **数据安全**：用户对话中的个人信息（护照号、出行日期等）在问道侧如何存储和脱敏？是否满足数据合规要求？

## 九、总结

```
┌─────────────────────────────────────────────────────────────┐
│                     影响最终效果的三角模型                      │
│                                                             │
│         ┌──────────────┐                                    │
│         │  Skill 质量   │ ← Prompt Engineering              │
│         │ (描述+few-shot)│                                   │
│         └──────┬───────┘                                    │
│                │                                            │
│    ┌───────────┼───────────┐                                │
│    │                       │                                │
│    ▼                       ▼                                │
│ ┌──────────────┐    ┌──────────────┐                        │
│ │ API 友好程度  │    │ 问道平台能力  │                        │
│ │ (BU后端改造) │    │ (编排/卡片/  │                        │
│ │              │    │  多轮/评测)  │                        │
│ └──────────────┘    └──────────────┘                        │
│                                                             │
│  三者任一短板 → 最终体验受限                                   │
│  推荐一期：Skill 质量 > API 友好化 > 问道新能力                │
└─────────────────────────────────────────────────────────────┘
```

**核心结论**：
1. **现有 API 的"AI 友好度"是最大变量** — 决定了能做方案 A/B/C 中的哪一档。
2. **Skill 是"零代码"的前提是问道平台基建到位** — 意图路由、参数抽取、追问、调用链路必须是平台通用能力。
3. **一期建议以方案 B（文本摘要）+ 单接口为目标**，BU 后端做轻量 AI 友好化改造（1~2 周），Skill 侧写好描述和 few-shot（3~5 天），即可在签证场景验证跑通，再横向推广其他 BU。
